## What was built (plain words)
In Settings, under the model setting, "Test it" runs the saved model over the 31 public worked cases that ship with the app. Each case goes through the **same** reading call and verifier a real pre-check uses (`requestPrefill` and `verifyPrefill`; there is no second path). The screen shows "Case n of 31", the line "Each case gets 60 seconds.", and a Stop button. At the end it says how often the model's fills would have reached the right verdict, how each question came out (right, left blank, wrong), how many fills the verifier dropped, how many cases got no usable answer, and that these 31 cases are public examples and no guarantee. It also says the numbers cannot be compared with the 2026-10-04 comparison. The result is saved (newest first, latest 20) and the model's label, on Settings and on the description screen, then reads "tested N/31 on DATE (measured as if you check every filled answer)". A stopped run never makes a model "tested".

### How a case is scored
1. The case's recorded graph (from `backtest/cases.json`) is the known correct answer. A reading that returns nothing usable (timeout, refusal, unreadable reply, nothing the verifier kept) scores every scored question blank and the verdict "no answer" (not matched).
2. For each select question, the question is **scored only when it is expressible**: exactly one option, run through the real answers-to-graph mapping on the question's own base, gives the gold graph's fields for that question. Otherwise it is "not scored" for that case: left out of right/blank/wrong and out of the overlay.
3. For a scored question: right = pre-filled with options that reproduce the gold; blank = not pre-filled; wrong = pre-filled with anything else.
4. The verdict: the gold graph, with each scored and pre-filled question's own fields replaced by what that answer gives through the real mapping, is run through `evaluate()` and compared with the recorded status and tier in `backtest/engine-verdicts.json`. Because the person is assumed to tick every fill and answer every blank correctly, this measures only the harm a wrong fill can do.

### What "expressible" excluded (measured on the real corpus)
- 18 select questions can be scored at all (`3aWhich` cannot be shown by the shipped policy). 31 cases x 18 = 558 question-case pairs; **251 are scored, 307 are not**. Each case scores between 5 and 12 questions.
- Never scored for any of the 31 cases: Q13 and Q14 (the corpus graphs carry no agent-access fields), Q3supplier and Q3a (no corpus case uses them), and `3aWhich`.
- Scored in, per question: Q11 30, Q12 30, Q7 29, Q9 27, Q4 26, Q5 17, Q3platformZone 15, Q4a 14, Q3 13, Q6 13, Q6a 13, Q8 13, Q6b 6, Q10 5. The big gaps: Q10 (two options, "my team" and "wider", both give "at scale", so on an at-scale gold two options reproduce it and it is not scored: 26 cases), Q3 (18: an internal build in Zone B has no option), Q6 and Q6a (18 each: the form defaults a blank follow-up to a stricter bindingness than an advisory gold), Q8 (18: no gold decision type, and "other" writes "unspecified"), Q5 (14: "everyday" and "typed only", and "not sure" and "confidential", give the same class).

## Deviations from Spec
1. **The label wording.** The chunk prompt summarises the label as "tested — {matches} of 31". The spec and test cases (GI-12-02, GI-12-06) pin "tested {matches}/31 on {date}" plus the suffix; B built that and F keeps it.
2. **Partial label (the B carried minor).** Both of the contract's wordings are kept: a stopped run still reads "a partial test stopped after N of 31 cases" (MS-4-09), and a partial run that was **not** stopped (inconsistent stored data only) reads "ran N of 31 cases". `ModelLabel`'s `partial` kind gained `stopped: boolean`; B's three data expectations and one words test were updated to carry it (each now asserts more, none loosened).
3. **`QUESTION_FIELDS` is a function of the policy** (`questionFields(policy)`), not a module constant; the pinned snapshot is generated from the shipped policy.
4. **The overlay uses the real mapping for the whole pre-filled set**, so a Question 5 reply ticking two kinds of information overlays two input nodes. The spec's phrase "the single resulting data class" predates R16-B's one-node-per-kind mapping; the real mapping is the contract's own rule ("reuses `plainAnswersToFormValues`").
5. **Spec §27.11 "stop at case 12" wording.** MS-4-08 says "Case 12 of 31", then after Stop "Stopped after 12 of 31 cases." For one run these cannot both hold, because the case in flight when Stop is pressed is not counted (NF-1-05, "no case scored after Stop"). Built: stopping while case 12 is read reports "Stopped after 11 of 31 cases."; stopping after 12 finished cases (case 13 in flight) reports 12 (both tested).
6. **A model setting that changes during a run stops it** (the result is saved as stopped, for the model that was tested). Not in the spec; without it a run could send corpus text to an address that is no longer the saved one.
7. **A run abandoned by leaving Settings is not saved.**
8. **`noAnswer` added to the result record** (optional, so earlier saved results still read) so a dead server reads "0 of 31 with 31 cases with no usable answer" rather than only "0 of 31".
9. **Per-question lines show the cases scored** ("cases scored: 7"), so the denominators are visible; and a note says a question is left out of a case when the form has no single matching answer.
10. **The verdict match compares status and tier only**, as §27.11 says. Track, controls and downstream reviews are not compared, so some wrong fills (Questions 9 and 12) never change a verdict.
11. **The mode that worked (format or tool) is carried from case to case inside the run only**; the run writes nothing to the saved setting, so a test cannot change what the next real pre-check tries first.
12. **Test ids:** spec-parity R7 allows an id in one test only, so a second test of the same case carries the words, not the id.
13. `engine-boundary.test.ts`: the "reply types and evaluate in one file" allow-list gained `engine/question-fields.ts` (the spec names the scorer as that exception), and a new test (GI-12-07) pins who may import the scorer.

## Surfaced Requirements
- **Drift test limit:** a model never fills a free-text answer (a typed supplier name, an "other" decision, a model name), so those three values are the only ones the overlay cannot carry. The drift test builds the form's side without them (two of the 19 subjects need that).
- The coverage of the test is thin for some questions (Q10: 5 cases; Q6b: 6; Q13, Q14 and Q3a: none). That is a property of the corpus and the spec's "expressible" rule. If the owner wants the test to speak about agentic questions, the corpus needs cases with agent-access fields; an owner decision, not F's.
