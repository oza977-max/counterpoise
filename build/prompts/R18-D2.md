## Chunk Summary

Two things.

1. **Write the record.** When a person confirms a case, write once where every answer came from, as `answer_sources` on that `graph_confirmed` event (or on `verdict_corrected` for a correction). This covers typed answers, model-filled answers they ticked, answers they changed, and answers carried from an earlier record. Each row records whether its quote is still in the final description. D1's register display then shows real cases, not only imported ones.
2. **Correct a case from the register.** In the submitter view only, the register detail gets a "Correct this check" action. It reopens the case on the form with every answer restored from the record:
   - typed stays typed;
   - confirmed pre-fills stay confirmed, with their quotes;
   - a `from_earlier_record` row comes back as an unconfirmed `record` answer that needs its tick.

   The existing correction flow then applies. Back is refused, and the result is a `verdict_corrected` event.

**This is the audit trail, so it is append-only evidence.** Any path that can write twice is a data-integrity bug. Double-click and StrictMode must not produce two writes; use the existing confirm lock or a synchronous `useRef` guard. A failed evaluation's retry writes its own `graph_confirmed`, carrying the same sources. That is existing behaviour, and the spec states it.

## Deliverables

1. **`toAnswerSources(answerState, description): { reads; answers }`** goes in `src/engine/answer-sources.ts`. It is pure and deterministic: rows in the form's question order, and `reads` de-duplicated in first-seen order.
   - Write the shape exactly as §27.13 and D1's handover say. Question 2 is never a row.
   - Map the origins:
     - `typed` → `typed`
     - confirmed `prefilled` → `prefilled_confirmed`, with `quotes`
     - `changed` → `prefilled_changed`, with `changed_from`
     - `record` → `from_earlier_record`
     - `not-carried`: per §27.10. If unanswered it is not a row; once answered it is `typed`.
   - `quote_in_final_description` uses C2's `quoteStillInText`.
   - `read` is an index into `reads`.
   - Respect D1's bounds. The form caps typed text at 200, so an export always fits.
   - Round-trip property: `readAnswerSources(toAnswerSources(x))` shows the same origins and counts that C2's confirmation line shows for `x`.
2. **The single write.** In `IntakeFlow.tsx` `runConfirmAndEvaluate`, call it once per confirm attempt, under the existing confirm lock, and put the result on that `graph_confirmed`, or on `verdict_corrected` for a correction.
   - No other writer.
   - The retry after `EVALUATION_FAILED` carries the same sources (C2 threads `answerState` through).
3. **The corrected description on `verdict_corrected`.** Write it when the confirmed text differs from **the currently effective description**: the latest correction's description if one exists, otherwise `use_case_created`'s.
   - This closes D1's pass-1 minor: a correction that reverts the text would otherwise leave a stale "as corrected" description showing.
   - Update §27.13 "The corrected description" in md and html, and add a changelog row dated 2026-10-22.
4. **The register action.** `RegisterDetail` shows "Correct this check":
   - only in the submitter (1LoD) view;
   - only for a case whose current record carries `answer_sources`. Cases without them are E's.

   Pressing it dispatches `OPEN_CORRECTION_FROM_RECORD` (new, in `intake-state.ts`) with `answersFromRecord(record)`. That is a pure function, beside `toAnswerSources`, that rebuilds `FormAnswerState`. Set `useCaseId` and `originalVerdictId` so `STEP_BACK` is refused and the existing correction flow and `verdict_corrected` apply.
   - Check how the existing "change an answer / correct verdict" flow is reached today (`handleCorrectVerdict`, `CORRECT_VERDICT_WITH_FORM`, `lastConfirmed`). Reuse it; do not build a second correction path.
   - Close the R18-A forward note: when `lastConfirmed` is gone, for example after a reload on the verdict screen, `handleCorrectVerdict` falls back to the retired card review. For cases with `answer_sources`, route it through `answersFromRecord`. Leave the older-case fallback to E, with a comment, and mark the forward note accordingly.
5. **No model call** on opening a correction from the record. `lastRead` should be seeded so that an unchanged description makes no call. Decide the right seed from §27.6/§27.7 and record the decision.

## TDD Approach (TDD-1)

1. **Red first: an outside-in acceptance test.** Commit it alone and record the SHA. It uses a fake model fetch from `src/llm/test-utils.ts` and a valid this-computer setting.
   1. Describe a case, read it, tick both pre-filled answers, change one other answer, and confirm through to a verdict.
   2. Open the register. The case detail shows the D1 lines for this real case, and the audit trail holds exactly one `graph_confirmed` with `answer_sources`.
   3. Press "Correct this check" in the submitter view. The form opens with the answers restored, the ticks kept, the quotes shown, and Back refused.
   4. Change one answer and confirm. A `verdict_corrected` event carries the new sources.
   5. Switch to the 2LoD view. "Correct this check" is not shown.
2. **Then units.** Write unit tests for `toAnswerSources` and `answersFromRecord`, with a fast-check round-trip property. Then the reducer action, then the components.
3. **Double-write tests.** Cover a double-click on Confirm, a StrictMode mount, and a failed evaluation followed by a retry. Assert the event count, not just the presence of an event.
4. **Make the acceptance test pass** and record the Green SHA.

## Review Criteria

Review against the expert principles, BC-001…006 and the defect classes:
- References;
- Contracts: `AnswerSourceRecord` written exactly as D1 reads it;
- Completeness;
- computed-but-never-consumed fields.

Attack these:
- two `graph_confirmed` events from one confirm;
- sources lost on retry;
- a `prefilled` answer written as `typed`;
- Question 2 written as a row;
- an unconfirmed answer written;
- the action visible to 2LoD;
- a correction that can step Back to the description;
- a model call on opening a correction;
- a stale corrected description;
- `answersFromRecord` trusting an imported, self-asserted record. It must be bounded and type-checked. Unknown origins become blank, unconfirmed answers, never "confirmed".
