Verdict
Build with caveats

As first written the design could not be built (two Critical findings, 69 Important). Three review rounds and three fix rounds closed every Critical and Important finding that any panel raised. The caveats: (1) the third fix round has not itself been reviewed; (2) several decisions the author took are awaiting owner ratification; (3) the live server replies behind the failure messages have not been captured yet (chunk R18-C0); (4) each build chunk runs its own review loop, which is where remaining defects are expected to surface.

Findings

All findings of all rounds were presented to the owner before any disposition (rule 28); the owner chose "fix all" after Round 1 and again after Round 2. None was deferred or dismissed. The full per-finding lists are in the panel reports of this session and the consolidated Round 1 list is kept with the review working files. Below: the six Critical findings, then the Important findings by round.

Critical (6, all closed)

DR8-C1 — Per-answer state never reaches the record (Round 1; five panels)

The design added the "who supplied this answer" state only to the form step; the baseline carries only plain answers through the later steps and the confirm write, no chunk owned the writer, the answer source had no record variant, and the state lived in two stores with no precedence.

Closed by: §27.6 (one answer-state object carried through every step, a derived plain-answers cache, one draft writer, mergePrefill) and §27.13 (written once per confirm attempt).

DR8-C2 — A false sentence in the build plan (Round 1)

The plan said the old model call was rebuilt for the reasoning-trace caller; that caller does not use it, and three readers of the old settings keys were unlisted.

Closed by: §27.8 and guide §12.4 list every old-key reader and the seed constant.

DR8-R2-C1 — The form question data lived in UI code but engine modules needed it (Round 2)

Option keys, kinds and conditional-option data sat in plain-copy.ts and StructuredForm; the engine boundary forbids importing them.

Closed by: New engine module question-structure.ts (no words); words passed in as a parameter; a test that structure and words cover the same ids.

DR8-R2-C2 — Edit-and-return could not be built as written (Round 2)

A stale form draft would beat a fresh pre-fill; two code paths wrote the draft key; the description lived in two places; the reducer had no Back path.

Closed by: updateFormDraft (single writer), mergePrefill before the form mounts, Question 2 bound to state.description, STEP_BACK transitions.

DR8-R3-C1 — Back from the form could turn a correction or a retry into a fresh case (Round 3; confirmed by three panels)

description_entry carries no case id; the baseline refuses exactly this for the old review screen. The new Back had no guard and would also have written the duplicate decision twice.

Closed by: §27.1: Back refused whenever useCaseId, originalVerdictId or afterFailedEvaluation is present; decidedFor skips the second duplicate check.

DR8-R3-C2 — The register had no "Correct" entry and keeps no graph (Round 3; one panel)

RegisterDetail does not pass onCorrect; the full graph is deliberately not persisted, so the old graph-based restore had no input for an older case and the three GI-10 cases could not be built.

Closed by: §27.10: a submitter-side "Correct this check" action; answers restored from recorded values (new cases) or from the description and recorded "Not sure" answers (older cases); the graph-based restore replaced by answersFromRecord.

Cross-Panel Themes

Theme A: One fact, two owners

The answer state, the description, the last-read marker and the plain answers each had two homes in the first design. Each fix round replaced "two owners" with one owner plus a derived copy, and each time a signature or chunk assignment elsewhere still named the old arrangement.

Theme B: Claims about the baseline that were never true

The reasoning-trace rebuild; "one place a graph is built"; "the register can correct"; "the app opens from file://"; "eleven examples"; "the draft effect saves nothing for evaluation_pending". Every one was caught by a panel reading the real code, not the spec.

Theme C: Honest wording that the app cannot prove

"Never leaves your computer", "confirmed by you", "tested N/31", the digest and the dropped-fills line each needed a condition, a qualification or removal.

Theme D: Chunk plans that put a case or a helper before its builder

Repeated in all three rounds; the ownership table (guide §12.5) is now explicit per family and per part.

What Prevents a Higher Score

  • Structural soundness (5–6): the reducer, form-draft and register changes touch the same large files (IntakeFlow.tsx, intake-state.ts, StructuredForm.tsx). The revision names owners, but only a build can show the transitions are complete.
  • Interface contracts (6): three signatures disagreed between sections in Round 3; they were reconciled by editing, not by a compiler. The first type-check run will find any that remain.
  • Implementability (6–7): the failure-message matchers are provisional until real server replies are captured (R18-C0); the scoring overlay and the older-case restore are specified by rule, not by example.
  • Requirements coverage (7): several requirement bodies carry amendments that await the owner's ratification.
  • Quality attributes (7): the third fix round was not independently reviewed.
